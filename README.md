# Takeaway ordering platform

A multi-tenant online ordering platform for independent takeaways. One
codebase, one git repo, deployed separately for each shop as its own
Cloudflare Pages project. Each shop has its own domain, branding,
menu, KV storage and Stripe Connect account; code fixes and new
features ship to all shops at once.

Originally built for **Rico's Peri Peri** (York) and now generalised to
host additional shops.

## Repo layout

```
templates/               source HTML / manifest with {{token}} placeholders.
                         Shared across every shop. Build substitutes per-shop
                         values into public/ at deploy.
  order.html             menu + checkout
  thank-you.html         post-payment confirmation
  reset-password.html    password reset flow
  staff/index.html       PIN-gated orders dashboard
  staff/manifest.json    PWA manifest for the staff dashboard
  landing-default.html   minimal generic landing page (fallback when a
                         shop hasn't authored its own index.html)

data/shops/<slug>/       everything specific to one shop
  config.json            business info, theme colours, hours, delivery
                         zone, Stripe Connect ID
  menu.json              canonical menu (server-side prices)
  menu-visual.json       customer-facing menu (descriptions, photos)
  logo.png               shop logo
  index.html             (optional) bespoke landing page; if absent the
                         default landing template is used
data/shops/_template/    starter scaffold — copy to make a new shop
data/_active/            generated by build; the current shop's
                         config.json + menu.json (gitignored at runtime
                         but committed with Rico's defaults so deploys
                         still work if a build doesn't run)

public/                  build output Cloudflare Pages serves. Most
                         files here are generated by scripts/build-shop.js
                         from the active shop's data. A few (privacy.html,
                         terms.html, _headers, _redirects, robots.txt,
                         sitemap.xml) are static and shared.

functions/               Cloudflare Pages Functions (the backend)
  _middleware.js         security headers (CSP, HSTS, etc.)
  _lib/                  shared helpers
    config.js            loads data/_active/config.json
    menu.js              loads data/_active/menu.json
    email.js, postcode.js, customer.js, totals.js, ...
  api/
    config.js            GET public config + Stripe pk + slots
    menu.js              GET canonical menu
    order.js             POST create order
    stripe-webhook.js    POST Stripe events
    staff/, account/, marketing/ ...

scripts/build-shop.js    the multi-tenant build. Reads SHOP_SLUG, copies
                         the active shop's files into the locations the
                         code's static imports expect, and substitutes
                         {{tokens}} in templates/* into public/*.
                         Runs automatically via package.json postinstall.

docs/ADDING_A_SHOP.md    step-by-step runbook for onboarding a new shop
DEPLOY.md                Cloudflare environment setup (KV, secrets, etc.)
```

## How the multi-tenant model works

Each shop is a separate Cloudflare Pages project that points at this
same repo. The project sets one env var: `SHOP_SLUG=<slug>`. On every
deploy:

1. Cloudflare clones the repo and runs `npm install`.
2. `npm install` triggers the `postinstall` script
   (`scripts/build-shop.js`).
3. That script reads `SHOP_SLUG`, picks the matching folder under
   `data/shops/<slug>/`, copies the config and menu into
   `data/_active/`, copies the logo and visual menu into `public/`,
   and substitutes `{{tokens}}` from `templates/` into the
   customer-facing pages in `public/`.
4. Cloudflare deploys `public/`. The Functions bundle picks up
   `data/_active/config.json` and `data/_active/menu.json` via the
   static imports in `functions/_lib/`.

Code changes ship to every shop on push. Per-shop changes live in
`data/shops/<slug>/` and only affect that shop.

See [`docs/ADDING_A_SHOP.md`](docs/ADDING_A_SHOP.md) for the full
onboarding checklist.

## Local development

```sh
npm install
npm run dev   # runs build + wrangler pages dev (defaults to SHOP_SLUG=ricos)
```

Open http://localhost:8788. Card payments use Stripe test mode.

To preview a different shop locally:

```sh
SHOP_SLUG=<slug> npm run build
npx wrangler pages dev public --compatibility-date=2026-05-01 --kv ORDERS_KV --kv MARKETING_KV --kv SLOTS_KV --kv STAFF_LOGIN_KV --kv CUSTOMERS_KV
```

## Editing a shop's menu, prices, hours, postcodes

Edit the relevant file under `data/shops/<slug>/` (config.json,
menu.json, menu-visual.json), commit, push. That shop's Pages project
auto-redeploys. Other shops are unaffected.

## Adding a feature

If the feature should ship to every shop: build it normally — one
codebase, one rollout.

If a shop has asked for a feature that may or may not be wanted by
others: add a flag to `config.json` (e.g. `features.loyaltyPoints:
true`) and gate the feature on it. **Never fork the code for one
shop** — feature flags are the only sanctioned way to differentiate.
