# Native plugin — EposHardware (printer + cash drawer)

`EposHardwarePlugin.java` is a Capacitor plugin that drives the **built-in printer
on both of our devices** — the **Sunmi T2** (LumiPOS) and the **ZCS Z93** (LumiWEB)
— plus the T2's cash drawer, and stubs Stripe Terminal for Phase 3. It's **Java**
on purpose — a `cap add android` project is Java by default, so no Kotlin Gradle
plugin is needed. Product/device background: `docs/PRODUCTS.md`.

## It's wired in automatically — no manual steps
The `android/` project is generated by `cap add android` and is **gitignored**, so
**`app/scripts/inject-native.mjs`** (run by `npm run prepare:android` / `npm run sync`)
re-applies the wiring on every build:

1. copies `EposHardwarePlugin.java` → `android/app/src/main/java/uk/co/ricos/epos/`
2. rewrites `MainActivity` to `registerPlugin(EposHardwarePlugin.class)` (an app-local
   plugin must be registered; Capacitor only auto-loads installed plugin *packages*)
3. adds the Sunmi printer SDK to `android/app/build.gradle`:
   `implementation 'com.sunmi:printerlibrary:1.0.24'` — on **Maven Central** (jcenter
   is dead), which the Capacitor project already resolves from.
4. copies the vendor **ZCS SmartPos** SDK from `libs/` (`SmartPos_2.0.6_R260615.aar`
   — not on Maven, so it's committed) into `android/app/libs/` and wires a
   `fileTree(dir: 'libs', …)` dependency.

Keep the `package` line (`uk.co.ricos.epos`) matching `appId` in
`app/capacitor.config.json`.

## Two printer backends, one APK
The backend is chosen **at runtime, on every call** — never at build time, and never
once at `load()`:

1. **Sunmi** inner-printer (woyou) service bound? → print via Sunmi. *(T2)*
2. else **ZCS** SmartPos SDK comes up? → print via ZCS. *(Z93, and the Z90/91/92 siblings)*
3. else `{ ok:false, reason:'printer-not-connected' }` — surfaced to staff.

Two things about that order are deliberate:
- **Sunmi is tried first** because the ZCS probe costs a `sysPowerOn` + a 1s sleep on
  hardware with no ZCS board; a T2 would otherwise pay it on every print and look like
  it was hanging. The probe is capped at `ZCS_MAX_ATTEMPTS = 2` (covers a cold boot
  where the SDK starts just after we do, then settles).
- **Per call, not at `load()`**, because the Sunmi service binds *asynchronously* — a
  decision taken at load would wrongly pin "no printer" on a T2 that hadn't bound yet.

## Behaviour
- `printDoc({ ops })` — the primary path: a rich receipt built as an op list
  (`text` / `row` / `rule` / `image` / `feed` / `cut`) with alignment, size, bold and
  logo. Both backends implement the **same op vocabulary**, so the receipt design lives
  entirely web-side, ships via OTA, and never needs an APK rebuild.
- `printReceipt({ text })` — plain-text fallback for older bundles.
- `kickDrawer()` — pops the drawer via the ESC/POS pulse over `sendRAWData()` (portable
  across firmware; the drawer must be on the printer's RJ11 port). **Sunmi only** —
  a Z93 has no drawer port and correctly returns `drawer-not-connected`.
- On a device that is neither (a plain Android tablet) everything degrades to
  `{ ok:false }`, so the app is safe to run anywhere.
- **Can't be compiled/tested in the cloud sandbox** — smoke-test `printReceipt` /
  `kickDrawer` on the device.

## Phase 3 — Stripe Terminal (WisePOS E)
`collectCardPayment({ amountP, currency, orderDraft })` is still a stub
(`{ ok:false, reason:'terminal-not-wired' }`). Wiring it needs the Stripe Terminal
SDK + a connection-token endpoint — see `docs/PHASE3_TERMINAL.md`.

## Kiosk lock-down (optional, recommended for a till)
Use Android **screen pinning** / a launcher restriction, or Sunmi's MDM, so the device
runs only this app.
